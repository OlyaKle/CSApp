
# Архитектурный паспорт
## Сервис анализа производительности работы отдела с ИИ-помощником

(Свой вариант)

## 1. Назначение системы

Сервис получает сведения о задачах и проектах отдела, проверяет загруженные данные, рассчитывает показатели производительности, формирует отчёты и использует ИИ для выявления проблем и подготовки рекомендаций.

Для взаимодействия ИИ с функциями и данными системы предусмотрен MCP-сервер. Он предоставляет ИИ-клиенту ограниченный набор инструментов и ресурсов для получения аналитики и работы с рекомендациями.

ИИ не получает прямого доступа к базе данных и не выполняет бизнес-операции самостоятельно.

## 2. Предметная модель (по практической работе № 2)

В системе выделены четыре ограниченных контекста:

| Контекст | Ответственность |
|---|---|
| Управление задачами | Задачи, исполнители, сроки, этапы и рабочие процессы |
| Импорт данных | Загрузка рабочих данных и проверка корректности |
| Аналитика отдела | Расчёт показателей, формирование отчётов и дашбордов |
| ИИ-анализ | Поиск проблем и формирование рекомендаций |

Три агрегата и их корни:
- **Рабочая задача** — корень агрегата контекста «Управление задачами».
- **Пакет данных** — корень агрегата контекста «Импорт данных».
- **Аналитический отчёт** — корень агрегата контекста «Аналитика отдела».

Рекомендация рассматривается как объект модели контекста «ИИ-анализ», а не как отдельный агрегат.

MCP-сервер не является пятым DDD-контекстом и не владеет предметными данными. Он обеспечивает доступ ИИ-клиента к функциям существующих контекстов.

## 3. Архитектурное решение

Выбран **модульный монолит с асинхронной передачей событий**. Сервер развёртывается как одно приложение, внутри которого сохраняются четыре предметных модуля.

MCP-сервер проектируется как отдельный адаптер, который взаимодействует с серверным приложением через внутренний API. Он принимает запросы от ИИ-клиента, проверяет их структуру и права пользователя, вызывает необходимые функции приложения и возвращает ограниченный результат.

Состав архитектуры:

- **Web-клиент** — отображает данные, выполняет простые проверки ввода и отправляет команды.
- **ИИ-клиент** — понимает запрос пользователя и выбирает подходящий инструмент MCP.
- **MCP-сервер** — принимает запросы JSON-RPC, проверяет параметры и права пользователя, вызывает внутренний API и формирует ответ.
- **Серверное приложение** — реализует четыре DDD-контекста и их бизнес-правила.
- **PostgreSQL** — хранит задачи, пакеты данных, отчёты, показатели и рекомендации. База физически единая, но данные логически разделены по контекстам.
- **RabbitMQ** — передаёт доменные события между модулями и обеспечивает асинхронную обработку.

MCP-сервер не подключается напрямую к PostgreSQL, не выполняет SQL-запросы и не дублирует бизнес-логику. Все изменения проходят через соответствующие модули основного приложения.

RabbitMQ используется для асинхронных процессов: формирования отчёта, запуска ИИ-анализа и передачи событий о принятии или отклонении рекомендации. Обычное чтение отчётов через MCP выполняется синхронно.

### Интерфейсы MCP

Для первой версии предусмотрены три инструмента и два ресурса.

### 3.1. Инструменты

| Инструмент | Назначение |
|---|---|
| `get_report(report_id)` | Получение информации о существующем аналитическом отчёте |
| `get_department_metrics(period_start, period_end)` | Получение показателей отдела за выбранный период |
| `set_recommendation_status(recommendation_id, decision, expected_version, request_id)` | Принятие или отклонение рекомендации |

Идентификатор отдела не передаётся в параметрах инструментов. Сервер определяет его по проверенному контексту авторизации пользователя.

Инструмент `set_recommendation_status` изменяет данные и вызывается только после явного подтверждения пользователя. Массовое изменение рекомендаций не предусмотрено.

### 3.2. Ресурсы

| URI ресурса | Назначение |
|---|---|
| `report://{report_id}` | Получение сведений об аналитическом отчёте |
| `recommendations://{report_id}` | Получение рекомендаций, связанных с отчётом |

Ресурсы предназначены только для чтения. Они возвращают необходимые для анализа сведения без персональных данных сотрудников и лишней технической информации.

## 4. Основные потоки

### 4.1. Подготовка отчёта

1. Пользователь загружает данные.
2. Контекст «Импорт данных» выполняет `importData()` и `validate()`.
3. После успешной проверки пакет выполняет `approveForAnalysis()` и публикует событие `DataPackageApproved`.
4. Контекст «Аналитика отдела» получает событие, рассчитывает показатели и формирует отчёт.
5. После публикации `ReportGenerated` контекст «ИИ-анализ» начинает анализ.
6. Готовый отчёт доступен независимо от результата ИИ-анализа.

### 4.2. Получение отчёта через MCP

1. Пользователь формулирует запрос в ИИ-клиенте.
2. ИИ-клиент выбирает инструмент `get_report` и отправляет запрос в формате JSON-RPC.
3. MCP-сервер проверяет структуру запроса и параметры.
4. Пользователь определяется по проверенному JWT-токену.
5. Проверяются роль пользователя и принадлежность отчёта его отделу.
6. MCP-сервер вызывает внутренний API основного приложения.
7. Контекст «Аналитика отдела» проверяет данные и получает отчёт из PostgreSQL.
8. MCP-сервер возвращает ИИ-клиенту необходимые сведения.

### 4.3. Принятие рекомендации и изменение задачи

1. ИИ-анализ создаёт рекомендацию, после чего пользователь может ознакомиться с ней через ресурс `recommendations://{report_id}`.
2. Пользователь принимает или отклоняет рекомендацию.
3. После явного подтверждения вызывается `set_recommendation_status`.
4. Контекст «ИИ-анализ» проверяет текущий статус рекомендации и её версию, сохраняет решение и публикует событие `RecommendationAccepted` или `RecommendationRejected`.
5. Принятие рекомендации само по себе не изменяет рабочую задачу.
6. Изменение задачи выполняется отдельно через контекст «Управление задачами» после подтверждения пользователя и проверки правил агрегата «Рабочая задача».
7. При успешном изменении срока задачи публикуется `TaskDeadlineChanged`.

### 4.4. Одновременное изменение данных

Для изменения статуса рекомендации используется оптимистическая блокировка: передаётся `expected_version` — версия записи, которую видел пользователь.

Если запись уже была изменена, операция отклоняется без сохранения нового решения. Для защиты от повторного выполнения используется `request_id`.

MCP-сервер не реализует собственный механизм блокировки, а передаёт необходимые параметры в бизнес-операцию основного приложения.

## 5. Принципы согласованности

- Одна транзакция изменяет один агрегат.
- Между агрегатами передаются события, а не выполняется общая транзакция.
- Пакет с ошибками проверки не передаётся в аналитику.
- Отчёт формируется только по проверенному пакету и для одного отдела и периода.
- Повторная доставка команды не должна создавать дубликаты.
- Для изменения рекомендации используются `request_id` и `expected_version`.
- MCP-сервер не дублирует бизнес-правила и передаёт операции соответствующим контекстам.
- Принятие рекомендации не приводит к автоматическому изменению задачи.

## 6. Безопасность

### 6.1. Аутентификация и авторизация

Для проверки пользователя используется JWT, предусмотренный в предыдущей практической работе. Проверяются подпись и срок действия токена.

В доверенном контексте авторизации используются:
- `sub` — идентификатор пользователя;
- `role` — роль пользователя;
- `department_id` — идентификатор отдела;
- `exp` — срок действия токена.

Доступ к сводным показателям, отчётам отдела и изменению рекомендаций предоставляется руководителю. Сотрудник не получает через MCP доступ к общей аналитике отдела.

MCP-сервер не доверяет `user_id` и `department_id`, которые может передать ИИ-клиент. Эти значения определяются по проверенному токену.

### 6.2. Основные ограничения

- Изменение рекомендации выполняется только после явного подтверждения пользователя.
- Массовое принятие или отклонение рекомендаций не предусмотрено.
- Для ресурсов возвращаются только необходимые поля.
- Персональные данные сотрудников не включаются в общие ответы MCP.
- Текст отчётов и рекомендаций рассматривается как данные, а не как инструкции для ИИ.
- Все вызовы инструментов и обращения к ресурсам проверяются и журналируются.
- Частота вызовов ограничена 30 запросами в минуту на пользователя.
- Размер одного ответа не должен превышать 100 КБ.
- Период получения метрик ограничен 366 днями.
- Тайм-аут одного запроса составляет 10 секунд.

### 6.3. Защита от повторов и конфликтов

Для изменяющего инструмента используется `request_id`, предотвращающий повторное применение одной команды.

Для параллельных изменений применяется оптимистическая блокировка с помощью `expected_version`. Если версия записи устарела, операция отклоняется.

В журнал аудита записываются пользователь, ИИ-клиент, название инструмента, параметры, результат и код ошибки. Пароли и токены не сохраняются, персональные данные маскируются.
