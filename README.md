# Архитектурный паспорт
## Сервис анализа производительности работы отдела с ИИ-помощником

Учебный проект по дисциплине «Создание клиент-серверных приложений».

## 1. Назначение системы

Сервис получает сведения о задачах и проектах отдела, проверяет загруженные данные, рассчитывает показатели производительности, формирует отчёты и использует ИИ для выявления проблем и подготовки рекомендаций.

## 2. Предметная модель (по практической работе № 2)

В системе выделены четыре ограниченных контекста:

| Контекст | Ответственность |
|---|---|
| Управление задачами | Задачи, исполнители, сроки, этапы и рабочие процессы |
| Импорт данных | Загрузка рабочих данных и проверка корректности |
| Аналитика отдела | Расчёт показателей, формирование отчётов и дашбордов |
| ИИ-анализ | Поиск проблем и формирование рекомендаций |

Три агрегата и их корни:
- **Рабочая задача** — корень агрегата контекста «Управление задачами».
- **Пакет данных** — корень агрегата контекста «Импорт данных».
- **Аналитический отчёт** — корень агрегата контекста «Аналитика отдела».

Отдельный агрегат для рекомендации в практической работе № 2 не выделен. В архитектуре рекомендация рассматривается как объект модели контекста «ИИ-анализ», а не как четвёртый агрегат.

## 3. Архитектурное решение

Выбран **модульный монолит с асинхронной передачей событий**. Сервер развёртывается как одно приложение, внутри которого сохраняются четыре предметных модуля. Это соответствует разделению контекстов из практической работы № 2 и не добавляет сложности микросервисной инфраструктуры на этапе первой версии.

- **Web-клиент** — тонкий клиент: отображает данные, выполняет простые проверки ввода и отправляет команды.
- **Серверное приложение** — реализует четыре контекста и их бизнес-правила.
- **PostgreSQL** — физически единая база с логически разделёнными хранилищами/схемами контекстов. Модули не обращаются напрямую к таблицам друг друга.
- **RabbitMQ** — передаёт события и запускает асинхронную обработку.
- **Внешняя система управления задачами** — подключается через ACL, который преобразует её формат в модель проекта.
- **Внешний ИИ-сервис** — вызывается из контекста «ИИ-анализ» через адаптер/ACL, если форматы отличаются.

RabbitMQ — конкретный вариант реализации шины событий. В практической работе № 2 зафиксирована сама необходимость шины событий, но конкретный брокер не задавался.

## 4. Основные потоки

### 4.1. Подготовка отчёта
1. Пользователь загружает данные.
2. Контекст «Импорт данных» выполняет `importData()` и `validate()`.
3. Только после успешной проверки пакет выполняет `approveForAnalysis()` и публикует `DataPackageApproved`.
4. Контекст «Аналитика отдела» получает событие, рассчитывает показатели и формирует отчёт.
5. После публикации `ReportGenerated` контекст «ИИ-анализ» начинает анализ. Готовый отчёт доступен независимо от результата ИИ-анализа.

### 4.2. Принятие рекомендации и изменение задачи
1. ИИ-анализ создаёт рекомендацию и пользователь принимает или отклоняет её.
2. При принятии публикуется `RecommendationAccepted`.
3. Это событие передаёт информацию в контекст «Управление задачами», но **не изменяет задачу автоматически**.
4. Изменение задачи выполняется отдельной подтверждённой командой через правила агрегата «Рабочая задача».
5. При успешном изменении публикуется `TaskDeadlineChanged` (если менялся срок).

### 4.3. Одновременное изменение задачи
Для изменения используется оптимистическая блокировка: клиент передаёт версию задачи. Если задача уже изменена, сервер отклоняет запрос с конфликтом, а пользователь обновляет данные и повторяет действие.

## 5. Принципы согласованности

- Одна транзакция изменяет один агрегат.
- Между агрегатами передаются события, а не выполняется общая транзакция.
- Пакет с ошибками проверки не передаётся в аналитику.
- Отчёт формируется только по проверенному пакету и для одного отдела и периода.
- Повторная загрузка/доставка команды не должна создавать дубликаты.
- ИИ-рекомендация не обходит бизнес-правила управления задачами.

## 7. Допущения и границы

Практическая работа № 2 не фиксирует конкретные технологии, провайдера ИИ, механизм авторизации, численную нагрузку и SLA. Поэтому PostgreSQL, RabbitMQ, JWT и внешний ИИ API являются проектными предложениями для паспорта, а не решениями, уже подтверждёнными отчётом № 2. Нагрузка и требования к доступности должны быть уточнены перед реализацией.
