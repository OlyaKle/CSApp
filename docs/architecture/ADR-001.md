# ADR-001. Выбор модульного монолита с асинхронной обработкой

- **Статус:** принято для первой версии проекта
- **Дата:** 09.11.2026
- **Решение:** модульный монолит; RabbitMQ для фоновых задач и доменных событий; PostgreSQL для хранения данных.

## 1. Контекст

Разрабатывается сервис для анализа производительности работы отдела с ИИ-помощником. Система должна:
- управлять задачами и их сроками;
- импортировать сведения из файлов и внешних систем;
- рассчитывать показатели отдела и формировать отчёты;
- передавать результаты в ИИ-модуль для выявления проблем и подготовки рекомендаций.

Ранее выделены четыре ограниченных контекста: «Управление задачами», «Импорт данных», «Аналитика отдела» и «ИИ-анализ». Также определены агрегаты «Рабочая задача», «Пакет данных» и «Аналитический отчёт».

В первой работе отмечены проблемы аналогов: снижение производительности при большом количестве задач и фильтров, перегруженность интерфейса, зависимость отдельных возможностей от плагинов и сложность настройки рабочих процессов.

Точные сведения о будущей нагрузке, числе пользователей, составе команды и SLA пока не заданы. Поэтому решение рассчитано на первую версию продукта и должно допускать дальнейшее развитие.

## 2. Рассмотренные варианты

| Вариант | Преимущества | Недостатки |
|---|---|---|
| Монолит без модульных границ | Самый простой запуск и сопровождение | Со временем модули могут тесно переплестись; сложнее менять отдельные части |
| **Модульный монолит** | Один процесс развёртывания; ясные границы предметных областей; локальные транзакции; проще сопровождать небольшой команде | Масштабируется целиком; необходимо контролировать соблюдение границ модулей |
| Микросервисы | Независимое развёртывание и точечное масштабирование | Сложнее инфраструктура, мониторинг, сетевое взаимодействие и согласованность данных |

## 3. Критерии выбора

- **Time-to-Market:** для учебного MVP важен быстрый запуск.
- **Scalability:** разделение на модули позволяет оптимизировать наиболее нагруженные операции; при необходимости модуль можно выделить позднее.
- **Reliability:** сбой внешнего ИИ-сервиса не должен останавливать управление задачами и просмотр готовых отчётов.
- **Cost:** один серверный контур и одна основная БД дешевле в эксплуатации, чем набор микросервисов.
- **Maintainability:** отдельные модули, контракты и запрет прямого доступа к чужим таблицам снижают связанность.

## 4. Решение

Выбрать модульный монолит. Внутри приложения выделить четыре модуля:
1. Управление задачами.
2. Импорт данных.
3. Аналитика отдела.
4. ИИ-анализ.

Основное хранилище — PostgreSQL. Для длительных и фоновых операций использовать RabbitMQ. Клиент обращается к серверу через HTTP API. ИИ-модуль вызывает внешнюю ИИ-модель через API.

События, например `DataPackageValidated`, `ReportGenerated` и `RecommendationCreated`, позволяют запускать последующие действия без прямой синхронной зависимости модулей.

## 5. Последствия

### Положительные
- проще разработать и развернуть первую версию;
- предметные области разделены по модулям;
- длительные операции не блокируют пользовательский запрос;
- при росте нагрузки можно отдельно вынести импорт, аналитику или ИИ-анализ в сервисы.

### Отрицательные и ограничения
- приложение масштабируется целиком, даже если нагрузка выросла только в одном модуле;
- RabbitMQ добавляет отдельный инфраструктурный компонент;
- асинхронные операции требуют повторной обработки ошибок и контроля повторных сообщений;
- границы модулей нужно поддерживать архитектурными правилами и тестами.

## 6. Основные риски и меры снижения

| Риск | Мера |
|---|---|
| Рост нагрузки на построение отчётов | Фоновое формирование отчётов, индексы, оптимизация запросов; измерение времени выполнения |
| Недоступность ИИ-провайдера | Тайм-ауты, ограниченные повторы, статус «анализ ожидает повторной обработки»; отчёт остаётся доступен |
| Повторная доставка события | Идемпотентная обработка по идентификатору события |
| Нарушение границ модулей | Взаимодействие через публичные интерфейсы и события; запрет прямого доступа к чужим таблицам |
| Конфликт одновременного изменения задачи | Проверка версии записи и понятное сообщение пользователю при конфликте |

## 7. Условия пересмотра решения

Вернуться к вопросу перехода на микросервисы, если появится необходимость в независимой работе и выпуске модулей, сильно возрастёт нагрузка на отдельные части системы или единое развёртывание начнёт создавать проблемы. Само по себе увеличение количества функций не является причиной для перехода.
